Does a committed testability rule book change what a coding agent writes?

A controlled trial on a public open-source application. One prompt, two branches, one variable. Every diff, command and result on this page was produced by the runs described here.

Haseeb Mohammed·Hexagon

  • Session Testability as an Agent Skill
  • Runs 24–25 Sep 2026
  • Application mern-stack-example

01 / The questionWhether the rule book changes the code, not the tests

A coding agent asked for a feature will reason carefully about correctness. The question is whether it does anything at all for the people who have to test the result afterwards — and whether committing a testability rule book to the repository changes that.

The trial holds the application, the commit, the prompt and the model constant. The single variable is whether a rule book is present on the branch.

application
mongodb-developer/mern-stack-example — MongoDB's own MERN reference application, Apache‑2.0, actively maintained. React and Vite front end, Express and MongoDB back end, 17 source files.
why this one
Small, real, well maintained, and carrying zero test hooks: the data-testid count across the source is 0. Its list and navigation components contain no id attributes either.
branches
baseline → the application plus a Playwright harness and a test suite written in advance. no-testability is identical to it. with-testability adds the rule book, committed before the agent ran.
rule book
Three artifacts on the treatment branch only: an always-loaded baseline instruction file, an on-demand playbook of four testability categories with stack idioms, and a gate script that checks changed files.
sessions
Two fresh agent sessions with no shared history. Neither prompt mentions testability, hooks, conventions or tests.

The prompt, identical on both branches

Add a Date of Joining field to employee records: capture it when creating or editing an employee, store it, and show it in the list. Leave the cell blank when no date is set.

What neither run was allowed to touch

A twenty-test suite written before either run sat on both branches. An agent could add tests for behaviour it created; it could never edit the tests written in advance. Both runs complied.

04 / The findingWhat it got right, and what it never considered

Handled without being asked

  • Timezone-stable date handling, with a comment explaining the choice
  • A form input with id, name and an associated label
  • Absent values normalised consistently
  • The data model documented

Not considered at all

test hooks added0
input validatednone
error codes a test can assertnone
state reachable programmaticallyno

It solved everything it could reason about as correctness, and nothing that serves an outside observer — because nothing in its context said an outside observer exists.

That is the finding the session is built on, and it is why the rule book is a rule book rather than a code-review habit: it is the observer's needs, written where the author will read them.

07 / ConsequenceThen it wrote the tests

Unprompted, the treatment run added a twelve-test suite for the behaviour it had created: invalid date formats, clearing the field, the empty state, and a full form round-trip. Each test creates its own records over the API and cleans up after itself, so it depends on no shared state and runs in any order.

09 / LimitsWhat this does and does not show

Stated plainly, because they bound what the session claims.

  • One run per branch. Coding agents are non-deterministic. This is not a repeated trial and no statistical claim is made.
  • One application, one feature, one stack. Nothing here establishes a general effect size.
  • The rule book names an error-envelope convention, and the pre-written suite asserts that convention. Standardising an error shape is what a shared team convention is for — but it means part of the treatment's pass rate reflects a shape the rule book supplied. This is stated openly in the session.
  • The control could see the pre-written test suite and did not use it. The suite was left in place rather than hidden, so the control was not deprived of the requirements. That it did not apply them is part of the finding: the same information, positioned as tests rather than as rules, did not change what was built.
  • No test-stability measurement is made. The trial compares what was built, not flakiness across repeated runs.
  • One pre-written test is expected to remain red on the treatment branchconfirmation pending — it asserts a hook on a control living in a file the agent never opened. Verified from the diff; the suite run itself is outstanding. It is reported as a finding rather than smoothed over: rules apply to code as it is written, so an application converts incrementally.
